# Job_Map

**통근 시간 기반 채용 지도.** 직무로 공고를 검색하는 대신, 내가 사는 곳에서 도보·대중교통·자차로 실제로 닿는 범위를 지도에 그리고 그 안의 공고만 보여준다.

기존 채용 사이트는 `직무 → 공고 목록 → 주소 확인 → 지도 앱에 하나씩 찍어보기` 순서다. 이 프로젝트는 순서를 뒤집는다: `내 위치 → 통근 30분 권역 → 그 안의 공고`. 자취방에서 가까운 근무지가 중요한 사람에게 지금 이걸 한눈에 보여주는 서비스가 없다.

---

## 1. 범위

- **지역**: 전국. 수도권만으로는 사용자가 한정되고, 뒤에 나오는 데이터 상품이 전국 커버리지 없이는 팔리지 않는다.
- **직군**: 전 직군.
- **이동 모드**: 도보 / 대중교통(도보 접근 포함) / 자차(목적지 최근접 주차장까지 운전 + 주차장에서 목적지까지 도보).
- **필터**: 연봉, 학력, 경력, 고용형태, 직종.

---

## 2. 이 프로젝트의 자산은 무엇인가

통근 시간 필터 자체는 방어 가능한 기능이 아니다. 대형 채용 사이트가 마음먹으면 금방 붙인다. 실제 자산은 두 개다.

1. **정규화된 근무지 좌표 데이터셋** — 공고에 적힌 주소는 대개 본사이거나 `서울 강남구` 수준이거나 아예 없다. 실제 근무지를 지사·공장 단위까지 좌표로 확정한 데이터는 아무도 갖고 있지 않다.
2. **공고 시계열** — 채용 공고는 마감되면 원본이 사라지고 **소급 수집이 불가능하다.** 오늘 저장을 시작하지 않으면 1년 뒤에도 시계열은 0이다. 반대로 1년을 모으면 경쟁자는 1년을 기다려야 따라온다.

> 그래서 개발 순서는 지도가 아니라 **수집기가 먼저**다. 지도는 나중에 다시 만들 수 있지만 놓친 시계열은 못 만든다.

---

## 3. 수익 모델

무료 공개 지도는 매출원이 아니라 (1) 유입·PR, (2) 사용자 신고로 근무지 좌표를 교정하는 검증 루프, (3) B2B 영업 시 "실제로 쓰이는 데이터"라는 증명 역할을 한다. 매출은 그 위에 얹은 데이터 레이어에서 난다.

| 축 | 고객 | 단가 | 필요 조건 |
|---|---|---|---|
| **얼터너티브 데이터** — 상장사 지역별·직군별 채용 시계열은 실적 선행지표 | 자산운용사, 증권 리서치 | 연 수천만~수억 | 12개월+ 시계열. 국내 공급자 사실상 없음 |
| **상업용 부동산 / 상권 분석** — 채용 밀도는 주간 인구의 선행지표 (기존 카드매출 기반 상권 데이터는 후행) | 개발사, 리츠, 프랜차이즈 출점팀 | 구독 | 전국 커버리지 |
| **HR 입지 리포트** — "판교 vs 마곡 갔을 때 통근 45분 내 인재풀 규모·직군 구성·경쟁사 밀도" | 대기업 HR/전략 | 건당 수백만~수천만 | 통근 격자 + 좌표 데이터 |
| **공고 접근성 진단** — "이 공고는 통근 접근성 하위 18%다. 셔틀/재택을 붙이면 인재풀 3.4배" | 채용 담당자 | 저단가·반복·셀프서브 | 가장 빠른 현금 |
| **급여 × 지리 지도** — 지역 해상도가 있는 보상 벤치마크 (머서·WTW에 없는 축) | 기업 보상팀 / B2C 훅 | 구독 | 급여 데이터 정제 |
| **공공·지자체** — 청년 일자리 미스매치, 산업단지 유치 효과, 통근 사각지대 | 지자체, 공공기관 | 용역 수천만 | 전국 데이터 |
| **B2C 전환** — 합격 직후는 이사 결정 시점이고 우리는 그 사람의 근무지를 안다 | 부동산 중개, 채용 CPA, 자동차·보험 | 리드 CPA | 트래픽 |

도달 순서: **공고 접근성 진단(3~6개월) → 입지 리포트 + 부동산·상권(6~12개월) → 얼터너티브 데이터(12개월+)**. 마지막이 최종 목표고, 그때까지 버티는 연료가 첫 번째다.

## 4. 기술 선택과 이유

### 4.1 언어: TypeScript (프론트·백엔드 공통)

`TypeScript`는 언어, `React`는 UI 라이브러리, `Next.js`는 React 프레임워크다. 서로 대체재가 아니라 층이 다르다. 이 프로젝트의 결정은 **"Next.js(React)를 쓰고, 그것을 JavaScript가 아니라 TypeScript로 쓴다"** 이다.

**왜 JavaScript가 아니라 TypeScript인가**
이 프로젝트는 UI 앱이 아니라 데이터 파이프라인이다. 공고 객체 하나가 필드 20개를 달고 `수집기 → DB → API → 지도` 4단을 지나간다. JS라면 `salaryMin`을 어딘가에서 `salary_min`으로 오타 냈을 때 예외가 나지 않고 조용히 `undefined`가 적재되며, **그 사실이 몇 달 뒤에 발견된다.** 이 프로젝트의 자산은 되돌릴 수 없는 시계열이므로 조용한 데이터 오염이 최악의 실패 모드다. `NormalizedPosting` 타입 하나가 수집기가 5개로 늘어도 적재 코드를 하나로 유지시켜 준다.

**왜 프론트·백엔드를 같은 언어로 묶는가**
수집기가 만든 타입을 API가 소비하고 프론트가 렌더한다. 여기서 언어가 갈리면 스키마 드리프트가 반드시 생기고, 그 드리프트가 곧 데이터 오염이다.

**탈락한 백엔드 후보**

| 후보 | 탈락 이유 |
|---|---|
| Python | 강점인 pandas/geopandas가 필요한 지점이 없다 — 공간 연산은 PostGIS가 담당한다. 개발 환경에 미설치 상태이기도 하다 |
| Java/Kotlin + Spring | 견고하지만 램 소비가 크고 서버리스 무료 배포에 맞지 않는다. **월 0원 운영 전략과 정면 충돌** |
| Go | 성능 이득이 실제 병목(라우팅 엔진, DB)에 없고 프론트와 타입 공유가 불가능하다 |

> 예외: 알터너티브 데이터용 통계 분석(시계열 회귀, 실적 상관 검증) 단계에서는 Python을 추가한다. 같은 Postgres를 읽기만 하므로 결합도가 0이다. 지금 넣을 이유는 없다.

### 4.2 데이터베이스: PostgreSQL + PostGIS

이 프로젝트의 연산은 대부분 공간 연산(등시선 폴리곤 안의 공고 찾기, 근무지 최근접 주차장 찾기, 격자 집계)이다. 애플리케이션 코드가 아니라 **PostGIS 안에서 SQL로** 처리하는 것이 몇 배 빠르고 코드도 적다. `ST_Contains`, `ST_DWithin`, GiST 인덱스가 핵심이다.

### 4.3 지도: MapLibre GL JS (Kakao Maps SDK 아님)

성능 때문이다. 전국 공고 수만 건을 지도에 뿌려야 하는데 Kakao SDK 마커는 수천 개에서 프레임이 무너진다. MapLibre GL은 WebGL 기반이라 클러스터링으로 10만 포인트를 처리하고, 등시선 폴리곤 오버레이도 정석적으로 지원한다.

- 배경 타일: VWorld(국토부, 무료) 또는 OSM
- **주소·상호 검색만 Kakao Local REST API** — 지도 SDK 없이 REST만 사용. 한국 주소/상호 검색은 대안이 없다
- 포인트가 더 늘면 deck.gl 레이어 추가

### 4.4 라우팅 엔진: 자체 호스팅 (상용 길찾기 API 아님)

카카오/네이버 길찾기 API는 정확하지만 호출당 과금이고 결과 저장에 약관 제약이 있다. 무엇보다 순진하게 만들면 `사용자 N명 × 공고 M건` 만큼 호출해야 하고, 공고 5만 건이면 사용자 한 명의 검색에 5만 콜이다.

**해결 1 — 등시선(isochrone)**: "각 공고까지 몇 분?"이 아니라 "내 위치에서 30분에 닿는 영역"을 폴리곤 하나로 계산하고, 그 안의 공고를 PostGIS 공간 쿼리로 뽑는다. 5만 콜 → 1콜.

**해결 2 — 등시선 영구 캐시**: 출발지를 격자에 스냅해 `(격자, 모드, 분)` 키로 폴리곤을 저장한다. 같은 동네의 두 번째 사용자부터는 라우팅 엔진을 아예 호출하지 않는다. 엔진이 죽어 있어도 캐시된 지역은 계속 서비스된다.

**엔진**
- 도보 / 자차: **Valhalla** + OSM
- 대중교통: **OpenTripPlanner 2** + 국토부 표준 GTFS
- 자차 경로 = `출발지 →(운전)→ 목적지 근처 주차장 후보 →(도보)→ 목적지` 2구간 합산. 후보 중 총 소요시간 최소를 채택. 주차장은 국토부 전국 주차장 정보 표준데이터 사용

### 4.5 데이터 소스

크롤링 얘기에서 출발했지만, 대형 채용 사이트 직접 크롤링은 약관 위반이고 차단도 강하다. 수익화를 목표로 하는 순간 파이프라인 자체가 리스크가 된다. 그래서 우선순위를 이렇게 잡는다.

1. **고용24(워크넷) 채용정보 오픈API** — 공식 무료 API. 전국·전직군. 기반 소스 *(구현 완료)*
2. **schema.org `JobPosting` JSON-LD** — 기업 자체 채용 페이지에 Google for Jobs용으로 심어둔 구조화 데이터. 기계 판독용으로 공개된 것이라 법적으로 안전하고 품질이 좋다 *(예정)*
3. **국민연금 사업장 데이터** — 사업장별 실제 주소 + 가입자 수 + 업종. 상호 정규화 키로 조인해 지사 존재 여부와 실제 고용 규모를 보강한다 *(예정)*
4. **웹 검색 + LLM 주소 추출** — `회사명 + 지역명`으로 지사 주소를 찾아 3번으로 교차 검증 *(예정)*

## 5. 스키마 설계에서 중요한 두 가지

### 5.1 시계열은 "일별 행"이 아니라 "구간"으로

공고 5만 건 × 365일 = 1800만 행이 되어 무료 티어를 넘긴다. 대신 `posting.first_seen_on ~ last_seen_on` 구간으로 저장하고, 일별 활성 공고 수는 구간 겹침 쿼리로 복원한다(일 1회 이상 수집 전제). 내용이 바뀐 순간만 `posting_change`에 기록한다. 무손실이면서 저장량이 두 자릿수 적다.

### 5.2 수집 실패와 진짜 0을 구별해야 한다

수집기가 조용히 실패한 날을 "공고 대량 마감"으로 기록하면 시계열에 가짜 절벽이 생기고, **이것이 이 프로젝트의 유일한 회복 불가능한 손상**이다. 데이터 상품 전체의 신뢰도가 여기서 무너진다. 그래서:

- 매 실행을 `collect_run`에 기록한다 (`ok` / `partial` / `failed`)
- 소스를 **끝까지 다 읽은 실행(`complete`)에서만** 미관측 공고를 마감 처리한다
- `npm run stats`가 성공 실행이 없는 날, 즉 시계열 결측일을 항상 출력한다

## 6. 배포: 월 0원 구성

| 층 | 선택 | 비용 |
|---|---|---|
| DB | **Supabase** (Postgres + PostGIS) | 무료 |
| 수집기 크론 | **GitHub Actions** (하루 2회) | 무료 |
| 프론트 + API | **Vercel** (Next.js) | 무료 |
| 지도 타일 / 주소검색 | VWorld or OSM / Kakao Local API | 무료 |
| 라우팅 엔진 | Valhalla + OTP2 (Docker) | 아래 참고 |

라우팅 엔진만 무료 티어에 들어가지 않는다. 전국 OTP2는 램 8~16GB를 요구해 서버리스에 올릴 수 없다. 3단계로 간다.

1. **지금 (링크 공유 단계)** — 라우팅 엔진을 개발 PC의 Docker에 띄우고 **Cloudflare Tunnel**로 노출한다. 무료, 포트포워딩·고정IP·인증서 불필요, `https://*.trycloudflare.com` 주소가 바로 나온다. PC가 꺼져 있으면 라우팅만 멈추고 지도·공고 목록은 Vercel+Supabase에서 계속 살아 있다. 캐시된 등시선도 계속 서비스된다.
2. **상시 운영이 필요해지면** — **Oracle Cloud Always Free**: ARM Ampere 4코어 / 램 24GB / 스토리지 200GB 영구 무료. 전국 OTP2가 실제로 돌아간다. 단 서울·춘천 리전 ARM 재고가 자주 없어 인스턴스 생성에 며칠 걸릴 수 있다.
3. **그것도 막히면** — Hetzner ARM CAX21(램 8GB) 월 €6 수준. 최저 유료 마지노선.

## 6.5 보안

보안은 부가 기능이 아니라 설계 제약으로 다룬다. 전체 위협 모델과 방어는 **[SECURITY.md](./SECURITY.md)** 에 있다. 요약하면 이 프로젝트의 위험 지점은 세 곳이다.

1. **라우팅 엔진 무인증 노출** (가장 위험) — Valhalla/OTP2에는 인증 기능이 없다. 개발 PC를 터널로 노출하는 배포 계획상, URL이 유출되면 누구나 당신 PC의 CPU를 쓸 수 있다. Cloudflare Access + nginx 인증 프록시 + 엔진 포트 미노출 3중 계층으로 막는다 (`docker/`)
2. **SSRF** — 2차 수집기가 임의 기업 URL로 요청을 보낸다. 클라우드 메타데이터·내부망 접근 경로다. `safeFetch()` 를 유일한 외부 요청 경로로 두고 호스트 allowlist, DNS 사설대역 검사, 리다이렉트 차단을 적용한다
3. **사용자 위치 = 민감 개인정보** — 출발지는 사실상 집 주소다. 격자 스냅 후에만 저장·캐시·로깅한다 (`src/lib/grid.ts`)

절대 규칙 8개(TLS 검증 우회 금지, SQL 문자열 보간 금지, `dangerouslySetInnerHTML` 금지 등)는 SECURITY.md 0장에 있다.

## 7. 실행 방법

```bash
npm install
cp .env.example .env      # DATABASE_URL, WORKNET_API_KEY, KAKAO_REST_KEY 채우기

npm run db:check          # 연결 / TLS / PostGIS 진단 — 문제 원인을 특정해준다
npm run migrate           # 스키마 생성 (PostGIS 확장 포함)
npm run collect           # 공고 수집 + 적재
npm run geocode           # 근무지 좌표 확보 (배치, 쿼터 분리)
npm run stats             # 데이터 규모 / 좌표 정밀도 / 시계열 결측일 점검

npm run test:ingest       # 적재 경로 스모크 테스트 (실제 DB, 끝나면 정리)
npm run typecheck
```

`db:check`를 먼저 돌리세요. 연결 실패 원인(예시 값 미교체, IPv6 전용 direct 연결, 비밀번호 percent-encoding 누락, 자체 CA 인증서 필요, pooler 사용자명 형식)을 구분해서 알려줍니다.

`test:ingest`는 배치 적재 SQL을 실제 DB에서 검증합니다. 타입 검사로는 `jsonb_to_recordset` 컬럼 정의, 표현식 유니크 인덱스에 대한 `ON CONFLICT`, 시계열 구간 연장, 날짜 시간대 왕복이 맞는지 알 수 없습니다. 적재 로직을 건드리면 이걸 돌리세요.

첫 실행 시 `COLLECT_MAX_PAGES=2` 로 시작해 워크넷 API 필드 매핑을 확인한 뒤 전량 수집으로 넘어갈 것을 권한다. 매핑이 틀려도 `posting.raw`에 원본 payload가 전량 보존되므로 나중에 무손실로 재처리할 수 있다.

### 필요한 API 키

- **고용24 오픈API**: https://openapi.work.go.kr — 회원가입 후 인증키 신청 (무료)
- **Kakao Developers**: https://developers.kakao.com — 애플리케이션 생성 후 REST API 키 (Local API 무료 쿼터)
- **Supabase**: https://supabase.com — 프로젝트 생성 후 Database URI. SQL Editor에서 `create extension postgis;` 가 되는지 먼저 확인
