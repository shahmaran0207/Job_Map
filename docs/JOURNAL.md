## 2026-08-26 ~ 08-28 — 착수, 그리고 축 전환

### 시작점

*"자취방에서 가까운 근무지가 중요한 사람이 많은데 그걸 한눈에 보기가 힘들다"* 는 불편함에서 출발했다. 기존 채용 사이트는 `직무 → 공고 목록 → 주소 확인 → 지도 앱에 하나씩 찍기` 순서인데, 이걸 `내 위치 → 통근 30분 권역 → 그 안의 공고` 로 뒤집는 것이 아이디어였다.

### 첫 설계 판단

**비용 구조를 먼저 풀었다.** 순진하게 만들면 `사용자 N명 × 공고 M건` 만큼 길찾기 API 를 호출해야 한다. 공고 5만 건이면 사용자 한 명의 검색에 5만 콜이다.

해법은 방향을 뒤집는 것이었다. "각 공고까지 몇 분?" 이 아니라 **"내 위치에서 30분에 닿는 영역"을 폴리곤 하나로 계산**하고, 그 안의 대상을 PostGIS 공간 쿼리로 뽑는다. 5만 콜이 1콜이 된다. 여기에 출발지를 격자에 스냅해 `(격자, 모드, 분)` 키로 등시선을 영구 캐시하면, 같은 동네 두 번째 사용자부터는 라우팅 엔진을 아예 호출하지 않는다.

이 격자 스냅은 **개인정보 보호도 동시에 해결한다.** 사용자가 입력하는 출발지는 사실상 집 주소다. 격자로 스냅한 뒤에만 저장·캐시·로깅하면 캐시에서 개인의 집을 역추적할 수 없다.

**수집기를 지도보다 먼저 만들었다.** 공고는 마감되면 원본이 사라지고 소급 수집이 불가능하다. 지도는 나중에 다시 만들 수 있지만 놓친 시계열은 못 만든다.

### 스키마에서 중요했던 두 가지

**시계열을 구간으로 저장했다.** 일별 행으로 쌓으면 5만 공고 × 365일 = 1,800만 행이 되어 무료 티어를 넘긴다. `first_seen_on ~ last_seen_on` 구간으로 두고 일별 활성 수를 겹침 쿼리로 복원하면 무손실이면서 저장량이 두 자릿수 적다.

**수집 실패와 진짜 0을 구별했다.** 수집기가 조용히 실패한 날을 "대량 마감"으로 기록하면 시계열에 가짜 절벽이 생긴다. 이것이 이 프로젝트의 **유일한 회복 불가능한 손상**이라고 판단해, 소스를 끝까지 다 읽은 실행에서만 미관측 항목을 마감 처리하도록 했다.

### 실제로 잡힌 버그들

설계보다 이쪽이 더 값진 기록이다. 모두 **예외를 던지지 않고 조용히 데이터를 오염시키는** 유형이었다.

**① DB TLS 검증 우회** — 내가 처음 쓴 코드에 `rejectUnauthorized: false` 가 들어 있었다. 흔한 편법이지만 DB 연결이 중간자 공격에 노출된다. 제거하고 CA 인증서 검증을 필수화했다. 우회 플래그는 제공하지 않는다.

**② 날짜 시간대 왕복** — node-postgres 가 `date` 를 로컬 자정의 `Date` 로 파싱하고, 그것을 `toISOString()` 으로 문자열화하면 KST 에서 9시간이 빠져 **하루 전날**이 된다. 그 결과 **모든 공고에 매 실행마다 가짜 마감일 변경 이력이 쌓이는** 상태였다. 스모크 테스트가 잡았고, 타입 검사로는 절대 잡히지 않는다. `DATE` 를 문자열로 받도록 근본 차단했다.

**③ 적재 성능** — 건당 쿼리 4번 구조였다. 전국 10만 건이면 왕복 40만 번이고 왕복 30ms 만 잡아도 3시간이 넘는다. 수집이 늦어지면 시계열에 결측이 생기므로 이건 성능이 아니라 기능 문제였다. `jsonb_to_recordset` 으로 JSON 을 파라미터 하나로 넘겨 청크당 쿼리 1~2개로 바꿨다. Postgres 의 65,535개 파라미터 제한도 함께 피한다.

**④ 인라인 주석이 값에 섞임** — `.env` 에 `COLLECT_MAX_PAGES=0  # 0 = 무제한` 처럼 쓰면 dotenv 버전에 따라 주석이 값에 들어와 `Number()` 가 `NaN` 이 된다. 수집 페이지 상한이 조용히 깨지는 경로였다.

**⑤ 법정동코드 페이징 누락** — 행정표준코드 API 는 리·동까지 전부 반환하고 시군구 행이 그 안에 흩어져 있다. 첫 페이지(1,000행)만 읽으면 리가 많은 도의 뒤쪽 시군구가 통째로 빠진다. 경상북도 7건 → 24건, 전국 169건 → **269건**. 이대로 뒀다면 경북·충남 매물이 지도에서 사라지는데, *데이터가 있는데 없는 것처럼 보이는* 종류라 발견이 아주 늦었을 것이다.

### 채용 데이터가 막힌 과정

여기서 프로젝트가 흔들렸다. 접근 경로를 하나씩 실측했다.

| 소스 | 결과 |
|---|---|
| 고용24 채용정보 API | **개인회원 런타임 차단.** 활용신청은 자동승인 되었는데 호출 시점에 기관구분 `개인` 을 거부한다. 문서에 이 제한이 없어 호출해봐야 드러난다. 호스트 2종 × 파라미터 2종 × XML/JSON 5가지 변형 모두 동일 |
| 공공데이터포털 워크넷 | 자동승인이지만 **KOGL 제4유형 = 비상업적 이용만** |
| 사람인 오픈API | 심사. 근무지 해상도가 **시군구까지**(`서울 > 관악구`), 일 500회 |
| 잡코리아 API | **공공기관·학교 우선 제공.** 기업·개인은 내부 검토 |

중간에 "그럼 사람인을 크롤링하자" 는 방향이 나왔지만 접었다. **잡코리아가 사람인을 상대로 낸 소송에서 법원이 채용공고 크롤링을 저작권법상 데이터베이스제작자 권리 침해로 인정했다.** 하려던 것과 거의 동일한 행위이고, 그 사건의 피고가 사람인이었다. 무엇보다 사람인은 공식 API 를 제공하므로 크롤링할 이유가 없다.

결론: **승인에 의존하는 어떤 경로도 수익화를 지탱하지 못한다.** 채용 공고 데이터는 잡보드의 사업 그 자체여서 개방할 인센티브가 없다.

### 축 전환 — 통근 기반 거주지 지도

원래 구상의 **거울상**으로 옮겼다. "자취방에서 가까운 근무지" 대신 **"직장에서 가까운 거주지"**. 통근 엔진은 그대로다.

전환 근거는 데이터 구조의 차이였다.

| | 채용 데이터 | 국토부 전월세 실거래가 |
|---|---|---|
| 개인 접근 | 런타임 차단 | 자동승인 |
| 상업적 이용 | KOGL 제4유형 | **이용허락범위 제한 없음** |
| 트래픽 | 500회/일 | 10,000회/일 |
| 주소 해상도 | 시군구 | 건물 단위 |

정부가 개방 의무를 지는 데이터라 구조가 다르다. 그리고 수익 모델은 오히려 개선된다 — 사용자가 통근권과 예산을 확정한 **직후의** 트래픽이 부동산 업계에서 가장 값이 높고, 우리는 매물을 갖지 않고도 그 트래픽을 만든다. 실제 매물은 네이버부동산·직방 검색 딥링크로 넘긴다. 크롤링이 0이다.

**만든 것은 거의 버리지 않았다.** 핵심 자산은 좌표 해결 엔진이고 그건 도메인 중립이다. 채용 스키마와 수집기도 테스트 통과 상태로 남겨뒀다. JSON-LD 수집기가 준비되면 레이어로 얹어 `출근지 ↔ 거주지` 양방향을 완성한다.

### 핵심 자산 — 좌표 해결 엔진

공개 데이터는 좌표를 주지 않고 주소 해상도가 시군구~법정동 수준이다. 관악구 중심점으로 통근시간을 계산하면 구 하나가 동서 5km 이므로 "도보 30분 이내" 필터가 의미를 잃는다.

착안점은 **`고유명 + 지역` 키워드 검색**이었다. 실측:

```
상세주소 "성남시 분당구 판교역로 166" → (127.11045, 37.39530)
이름+지역 "카카오 경기 성남시 분당구"  → (127.11046, 37.39545)   약 1m 차이
"래미안대치팰리스 서울 강남구"        → 서울 강남구 삼성로51길 37
"헬리오시티 서울 송파구"              → 서울 송파구 송파대로 345
```

**정확도 낮은 좌표를 격리하는 것이 이 엔진의 절반이다.** 해결 실패나 중심점 폴백은 `commute_usable=false` 로 표시해 통근시간을 표시하지 않는다. 정확도 낮은 좌표로 통근시간을 계산해 보여주면 지도가 조용히 거짓말을 하게 되고, 그것이 이 제품에서 가장 나쁜 실패다.

### 문서를 믿지 않고 실측한 것들

**엔드포인트와 필드명은 문서가 틀렸다.** 실거래가 API 문서에는 필드명이 한국어(`보증금액`, `월세금액`)로 적혀 있지만 실제 응답은 영문 camelCase(`deposit`, `monthlyRent`)다. 문서를 믿고 매핑했다면 전 필드가 `null` 로 적재되면서도 예외는 나지 않는, 가장 찾기 어려운 형태로 깨졌을 것이다.

그래서 **탐색기 스크립트**를 먼저 만드는 방식으로 굳혔다. 후보 엔드포인트를 순회해 동작하는 것을 찾고 **실제 응답 필드와 값을 덤프**한다. 이 방식으로 워크넷·실거래가·법정동코드 세 API 를 모두 확정했다.

값 덤프로 잡은 가장 중요한 것은 **금액 단위**다. `deposit="70,000"` 은 7억원이다 — 만원 단위 + 쉼표 포함 문자열. 틀려도 예외가 나지 않고 시세만 1만배 어긋난다. 단위 테스트로 고정했다.

**행정구역이 바뀌어 있었다.** 광주광역시와 전라남도가 `전남광주통합특별시` 로 통합되어, 구 명칭으로 조회하면 데이터가 없다고 응답한다. 이것이 좌표 해결기에도 파급됐다 — 법정동코드는 통합 명칭을 쓰는데 지오코딩 결과 표기가 다르면 지역 검증이 둘을 다르다고 판정해 **광주·전남 전체가 통근 계산에서 빠진다.** 시도명 별칭 그룹으로 묶고 회귀 테스트를 추가했다.

### 첫 실측 결과 (강남구 2026-08, API 4회)

```
거래 1,343건 / 건물 564건
아파트     보증금 3.00억 / 월세 155만   79.8㎡
오피스텔   보증금 2,000만 / 월세  85만   24.7㎡
연립다세대  보증금 5,000만 / 월세  68만   30.0㎡
단독다가구  보증금 1,000만 / 월세  70만   33.0㎡
```

시세가 현실적이므로 금액 단위가 맞다는 것이 확인된다.

좌표 확정 결과:

```
아파트 215/215, 오피스텔 66/66, 연립다세대 271/271 → 전부 건물 정밀도
단독다가구 0/12 → 법정동 중심점
건물 기준 97.9% / 거래 기준 83.7%
```

**거래 기준 83.7% 가 정직한 숫자다.** 단독/다가구는 건물 1개가 수십 건의 거래를 대표하므로 건물 기준 비율은 품질을 과대평가한다. 남은 16%는 정부가 개인정보 보호로 지번을 제공하지 않는 구조적 한계다.

**판정: 제품이 성립한다.** 아파트·오피스텔·원룸(연립다세대)은 건물 단위 통근 계산이 100% 가능하다.

### 이 프로젝트에서 굳어진 원칙

1. **문서를 믿지 말고 실측한다.** 탐색기 스크립트를 먼저 만든다
2. **조용한 실패를 만들지 않는다.** 실패와 "진짜 0"을 데이터에서 구별한다
3. **정확도를 데이터에 명시한다.** 못 믿을 값은 격리하고, 격리했다는 사실을 표시한다
4. **원본을 보존한다.** 매핑이 틀려도 무손실 재처리가 가능하도록 `raw` 를 남긴다
5. **외부 데이터를 쓰기 전에 라이선스와 개인 접근 가능성을 확인한다.** 이걸 놓쳐서 축을 한 번 바꿨다

## 2026-08-29 — 전국 수집, 그리고 4개 도가 통째로 저품질이던 버그

### 전국 데이터 수집

최근 3개월 × 269개 시군구 × 주택 4종 = 3,228슬롯.

```
API 호출 3,264회 (예산 9,000)
거래 396,262건 / 건물 73,062곳 / 시군구 256개
0건 슬롯 583  실패 슬롯 0  적재 실패 0
```

일 10,000회 한도의 33%만 썼다. 슬롯당 1회를 거의 넘지 않았는데, 시군구 1개월 거래가 대부분 1,000건(페이지 크기) 이하라 페이징이 필요 없었기 때문이다.

0건 슬롯 583개는 실패가 아니라 **실제로 거래가 없는 조합**이다(지방 소도시의 오피스텔 등). 이 둘을 구별해 기록한 설계가 여기서 값을 했다. 구별하지 않았다면 "시세 없는 지역"으로 오염됐을 것이다.

### 실행 전에 잡은 버그: 일시적 실패의 영구 캐시

7만 건 지오코딩을 시작하기 직전에 발견했다. `kakaoFetch` 가 HTTP 오류·재시도 소진에도 `null` 을 돌려줘서, 호출부가 "주소 없음" 과 구별할 수 없었다. 그 결과가 `geocode_cache` 에 miss 로 저장되고, 재실행하면 캐시가 먼저 걸려 되살릴 수 없다.

**중간에 쿼터가 끊기면 남은 수만 건이 전부 영구 실패로 굳는 구조였다.** `GeocodeUnavailableError` 를 도입해 '일시적 불가' 와 '주소 없음' 을 분리하고, 배치는 이 예외를 받으면 남은 건물을 건드리지 않고 중단하도록 했다.

함께 병렬화했다. 순차로는 건당 왕복 200ms 로 4시간이 넘는다. 워커 6개 + 250건 배치 쓰기로 **초당 70건**이 되어 20분 안에 끝났다.

### 그리고 실제로 잡힌 버그: 도 이름 축약형

지오코딩 후 통근 계산 가능 비율이 거래 기준 68.3% 였다. 단독/다가구(구조적 한계)를 빼고도 **아파트 3,796곳이 시군구 중심점으로 떨어져** 있었다. 도로명주소가 100% 있는데도.

시도별 분포가 원인을 가리켰다.

```
경상남도 1,777   경기도    10
충청남도 1,407   인천광역시  6
경상북도 1,112
충청북도   872
```

실패의 **99.6%가 딱 4개 도**. 지방 주소가 어려운 문제가 아니었다.

라이브로 다시 물어보니 모든 질의가 building 정밀도로 성공했다. 즉 **질의는 성공했는데 결과를 우리가 거부**하고 있었다.

```
법정동코드: "충청남도"  → 접미사 '도' 제거 → "충청남"
Kakao 반환: "충남"                        → "충남"
            "충청남" ≠ "충남"  →  거부  →  중심점 폴백
```

`shortSido()` 가 접미사만 떼고 축약형을 몰랐다. 서울·경기·인천은 축약형이 정식명과 같아서 멀쩡했고, **충청남/충청북/경상남/경상북 네 도만** 걸렸다. 전라남·전라북은 통합 별칭 그룹에 이미 들어 있어 우연히 피해 갔다.

축약형 매핑을 추가하고 4개 도 회귀 테스트를 넣었다. `--improve` 재실행 결과:

```
아파트     3,797/3,803 (99.8%)
연립다세대    916/  919 (99.7%)
오피스텔      466/  478 (97.5%)
```

전체 통근 계산 가능 비율이 **거래 기준 68.3% → 75.5%** 로 올라갔다.

### 이 버그가 남긴 교훈

예외가 나지 않았다. 로그도 깨끗했다. 4개 도의 아파트가 조용히 3km 오차 중심점에 찍혀 있었을 뿐이다. **강남구만 검증했을 때는 100% 였다** — 서울은 축약형이 같으니까.

수도권 표본만으로 검증하면 지방에서만 나는 버그를 못 잡는다. 그리고 이걸 발견한 것은 테스트가 아니라 **"왜 이 숫자가 이렇지" 를 파고든 것**이었다. `stats:rent` 가 전략별·유형별 분포를 출력하지 않았다면 68.3% 를 그냥 받아들였을 것이다.

관측 지표를 만들어 두는 것이 테스트만큼 중요하다.

### 현재 상태

```
건물 73,062 (좌표 100%)   거래 396,262   시군구 256/269
통근 계산 가능: 건물 94.6% / 거래 75.5%
남은 24.5%는 전부 단독·다가구 (정부가 지번을 공개하지 않는 구조적 한계)
```

## 2026-09-05 — 수익화 방향: 소비자용 유료 리포트, 첫 기능은 2인 교집합 통근권

### 문제

지도를 실제로 써보면서 "이걸 돈 주고 쓸 이유가 약하다"는 게 명확해졌다. 지금 하는 일
(과거 실거래가를 통근시간으로 필터링) 은 네이버부동산·직방이 이미 무료로, 더 신선한
데이터(실제 매물)로 하고 있다. 차별화가 없으면 트래픽도 매출도 안 만들어진다.

### 검토한 방향

- **B2B(사무실 입지 최적화)** — 직원 주소 목록을 넣으면 전체 통근시간을 최소화하는
  사무실 입지를 찾아주는 도구. 지금 인프라를 그대로 뒤집어 쓸 수 있고 기업은 이런 데
  컨설팅비를 실제로 낸다. 다만 UX(다중 입력 최적화)와 판매 채널(B2B 영업)을 새로
  만들어야 해서 지금 트래픽 기반으로 키우기 어렵다 — 보류.
- **소비자 구독(알림)** — 이사는 1~4년에 한 번이라 구독은 금방 이탈한다. 반려.
- **소비자 일회성 유료 리포트** — 채택. 이사 시즌에 한 번 쓰고 끝나는 소비 패턴에
  맞는 모델. 여러 후보지를 비교하고 PDF로 저장하는 형태로, 12개월 시계열 데이터로
  "이 동네 최근 오르는 중" 같은 협상 카드도 같이 준다.

### 첫 기능: 2인 교집합 통근권

리포트에 넣을 첫 차별화 기능으로 "직장이 다른 두 사람이 함께 살 곳"을 골랐다.
커플·룸메이트가 각자 통근권을 계산해서 겹치는 지역만 걸러주는 도구는 지금 시장에
없다. 기존 인프라(지오코딩, `getIsochrone`, `/api/rents` 공간 쿼리)를 그대로 재사용할
수 있어서 구현 비용도 낮았다.

구현 방식(자세한 내용은 `app/api/rents/route.ts` 참고):
- 두 사람의 통근권을 각각 계산한 뒤 PostGIS `ST_Intersection` 으로 겹치는 영역만
  건물 필터에 쓴다.
- **1인 모드를 "area2 = area1인 2인 모드의 특수 케이스"로 취급하지 않고, 아예
  intersection 계산 자체를 건너뛰게** 했다 — 회귀 위험을 없애는 게 우선이라 코드
  경로를 분기했다(계획 단계에서는 하나로 합치는 안을 생각했었는데, 구현하면서 안전한
  쪽으로 바꿈).
- 겹치지 않는 경우(`ST_IsEmpty`) 는 `rent_deal` 조인 쿼리를 아예 생략하고 바로 빈
  결과를 반환 — 불필요한 조인 비용을 줄이고, 클라이언트에는 "가격 조건이 안 맞아서"가
  아니라 "지리적으로 안 겹쳐서" 임을 명확히 알린다.

## 2026-09-14 — 대중교통(OTP2) 라우팅, 전국은 이 PC로 안 되서 부산권만

### GTFS는 TAGO가 아니라 KTDB

국토부 표준 GTFS를 받으려면 국가대중교통정보센터(TAGO)에 등록해야 한다고 알고 있었는데,
실제로는 국가교통DB(KTDB, ktdb.go.kr)의 "정보공개 > 자료신청 > 교통망 GIS DB > 대중교통"
에서 받는다. 회원가입 절차 없이 일반이용자도 소속기관·목적만 적으면 무상으로 받을 수
있었다 — 생각보다 문턱이 낮았다.

### 전국 그래프는 이 PC로 안 된다 — OOM 두 번

받은 GTFS(전국, stop_times만 1.4GB)와 남한 OSM PBF(286MB)로 OTP2 그래프를 빌드하려니
이 개발 PC(RAM 15.4GB, Docker Desktop WSL2 VM 기본 7.45GB)로는 힙을 5GB, 8GB로 늘려봐도
스트리트-트랜짓 연결 단계에서 매번 OOM이 났다. `.wslconfig`로 VM을 10GB까지 잠깐 올려봐도
마찬가지였다 — 이 데이터 규모 자체가 이 하드웨어에 안 맞는다는 뜻이라 원복했다.

그래서 지역을 자르는 쪽으로 방향을 바꿨다. `osmium extract`(Docker의 ubuntu 이미지에
apt로 설치)로 OSM PBF를, GTFS는 stops→stop_times→trips→routes→transfers 순서로
참조 무결성을 지키며 스트리밍 필터링하는 Node 스크립트로 잘랐다. 처음엔 경남 전체로
잘랐다가(정류장 41,226개), 사용자가 "전국을 한 번에 못 하면 범위를 더 좁히고 품질을
올리자"고 해서 부산+인근 통근권(김해·양산·창원 일부, 정류장 22,249개)으로 다시 좁혔다.
그래프가 211MB→118MB로 줄면서 서빙 메모리 여유도 커졌다(Xmx4g→3g로도 안정).

### GTFS가 그동안 없어서 한 번도 테스트된 적 없던 버그 3건

GTFS를 처음 구했다는 것 자체가, `src/lib/routing.ts`의 대중교통 경로가 여태 한 번도
실제로 실행된 적이 없었다는 뜻이었다. 실제로 켜보니 버그가 세 개 나왔다:

1. **OTP2의 등시선(TravelTime) API가 기본적으로 꺼진 샌드박스 기능.** 시작 로그의
   "Features turned off" 목록에 `SandboxAPITravelTime`이 있는 걸 보고서야 알았다.
   `data/otp/otp-config.json`에 `{"otpFeatures":{"SandboxAPITravelTime": true}}`를
   추가해야 한다.
2. **API가 POST JSON이 아니라 GET+쿼리스트링.** 기존 코드는 도보/자차(Valhalla)와
   똑같이 POST JSON으로 호출하고 있었는데, OTP2의 TravelTime API는 GET만 받고
   `time` 파라미터도 ISO 오프셋 형식(`2026-09-15T08:00:00+09:00`)만 파싱된다.
   `"8:00am"`, `"08:00"` 둘 다 500 에러가 났다.
3. **nginx 프록시가 쿼리스트링을 안 넘기고 있었다.** `proxy_pass`에 고정 URI만
   써두면 nginx가 원래 요청의 쿼리스트링을 자동으로 붙여주지 않는다 —
   `$is_args$args`를 명시해야 한다. 안 그러면 OTP가 파라미터를 전부 null로 받아서
   `NullPointerException`으로 500을 낸다.

그 외에 `data/otp/`에 원본 GTFS 폴더를 정리 안 하고 남겨뒀더니 OTP가 그걸 별도의
빈 GTFS 피드로 인식해서 `missing required entity: Agency` 에러를 내기도 했다 —
OTP는 base 디렉터리에 있는 폴더도 GTFS 피드로 자동 인식한다.

### 출발 시각은 사용자가 직접 고른다

대중교통은 시간표 기반이라 도보/자차와 달리 "몇 시에 출발하느냐"가 등시선 결과에
영향을 준다. 처음엔 "평일 오전 8시"로 고정할까 했는데, 사용자가 "요즘 탄력근무제
하는 회사가 많은데 고정값은 안 좋다"고 해서 화면에서 직접 요일/시각을 고르게 했다.
등시선 캐시 키(`isochrone_cache`)에도 30분 단위로 반올림한 출발시각 슬롯을 추가해서
(`db/006_transit_departure.sql`) 캐시 히트율과 사용자 자유도를 같이 잡았다.

2. **GCP e2-micro**(1GB, 영구 무료) — 가입은 오라클보다 안정적이지만, "라우팅
   서버는 없애고 대중교통 하나만 얹으면 1GB에도 들어갈 수도 있다"는 아이디어였다.
   그런데 이것도 "100% 확실"은 아니었고, 사용자는 정확히 그 불확실성을 거부했다.
3. **Hetzner 등 유료 VPS**(월 6천~1만원) — 즉시 되고 안정적이지만 "무료가 아니면
   안 된다"는 요구와 안 맞았다.
4. **PC + Cloudflare Tunnel 상시 가동** — 이미 검증까지 끝낸 방법이었지만, 전기세
   문제로 거부당했다.

넷 다 막힌 상태에서 "그럼 언어를 바꿔서라도 서버 없이 되는 방법은?" 이라는
질문을 받고 나서야 방향을 완전히 틀었다 — **자체 서버라는 개념 자체를 없애는
쪽으로.**

### 해결: 호스팅된 API + 서버리스 함수 안에서 직접 계산

- **도보/자차 → OpenRouteService**: 전 세계 OSM 기반 무료 공개 API. 이메일
  가입만 하면 되고 카드가 아예 필요 없어 오라클 같은 가입 실패 리스크가 없다.
  하루 2,500건/월 40,000건, 도보 20시간·자차 1시간까지 등시선 지원 — 우리
  요구사항(최대 90분)을 전부 커버한다.
- **대중교통 → minotor**: GTFS를 압축 protobuf 바이너리(timetable+stops, 우리
  부산권 데이터는 합쳐서 약 16MB)로 미리 컴파일해두고, Vercel 서버리스 함수
  안에서 RAPTOR 알고리즘을 직접 돌리는 라이브러리. **서버라는 게 아예 없다** —
  DB(Supabase, `transit_graph` 테이블에 bytea로 저장)에서 그래프를 한 번 읽어
  모듈 스코프에 캐싱해두고 그 안에서 쿼리한다.

minotor는 GTFS 파싱까지는 해주지만 "임의의 출발 좌표에서 등시선 폴리곤"까지는
안 만들어준다 — 거기까지는 직접 짰다: `stopsIndex.findStopsByLocation()`으로
가장 가까운 정류장을 찾고, 그 정류장을 RAPTOR 원점으로 삼아 `RangeQuery`를
"출발시각=도착시각(창 없음)"으로, 목적지를 빈 Set으로 줘서(minotor 문서가
"full-network mode"라고 부르는 방식) 전체 도달 가능 정류장의 최단 소요시간을
받는다(`RangeResult.allShortestDurations()`). 각 도달 정류장에 남은 시간만큼
도보 반경 원을 그리고, `@turf/turf`의 `union()`으로 전부 하나의 MultiPolygon으로
합친다. 순수 도보 반경(대중교통을 아예 안 타는 경우)도 원 하나로 얹는다 — 예전
OTP2의 `modes=WALK,TRANSIT` 과 같은 개념이다.

두 번 겪은 삽질:
- `transportModes` 를 빈 `Set()`으로 명시했더니 "모든 교통수단 허용"이 아니라
  "전부 금지"로 해석돼 등시선이 텅 비었다 — 아예 호출을 생략해야 기본값(전체
  허용)이 적용된다. minotor의 공개 API에 `ALL_TRANSPORT_MODES` 상수가 없어서
  (내부에만 있음) 명시적으로 지정할 방법이 없다.
- Windows Git Bash에서 `/tmp/...` 경로로 미니터 바이너리를 읽으려다 실제로는
  `C:\tmp\...`로 해석돼 파일을 못 찾았다 — WSL/POSIX 경로 오해는 이 프로젝트에서
  반복되는 함정이다.

### 이번 전환으로 사라진 것과 남은 것

`docker/`(Valhalla+OTP2+nginx 인증 프록시)를 통째로 지웠다. `ROUTING_URL`/
`ROUTING_TOKEN` 환경변수, `routing:up`/`routing:down`/`routing:logs` npm 스크립트,
로컬 엔진 타임아웃 분기(`src/lib/routing.ts`의 `isLocalRoutingHost`)까지 전부
없앴다 — SECURITY.md의 "라우팅 엔진 무인증 노출" 위협도 이제 존재하지 않는
위협이라 통째로 다시 썼다.

`isochrone()` 의 외부 시그니처와 `isochrone_cache` 의 캐시 키 구조는 그대로
유지했다 — 그래서 `app/api/rents`, UI(`FilterPanel.tsx`, `page.tsx`)는 거의
안 건드렸다. 어제 만든 "대중교통 출발 요일/시각을 사용자가 직접 고르는" UI와
캐시 슬롯(`db/006_transit_departure.sql`)도 그대로 유효하다.

트레이드오프: minotor는 정류장까지 걷는 구간을 직선거리로 근사한다(OTP2는 실제
도로 기반이었다). 정밀도 개선은 ORS Matrix API로 격자↔정류장 도보시간을 미리
계산해 캐시하는 2단계로 미뤘다 — 지금은 "서버 없이 막힘없이 동작하는 것"을
먼저 완성했다.

## 2026-09-15 (계속) — 실제 배포하면서 두 번 더 걸려 넘어졌다

바로 이어서 Vercel 배포까지 끝냈는데, 여기서도 두 가지를 실전에서야 알았다.

### `.env`가 첫 배포에 통째로 업로드될 뻔했다

`.vercelignore`를 새로 만들면서 `.env`를 빼먹었다. `data/`(3.2GB)를 제외하려고
`.vercelignore`를 만드는 순간 `.gitignore`는 더 이상 안 쓰이는 것으로 보였고
(`.gitignore`에는 `.env` 제외 규칙이 있었지만), `.vercelignore` 쪽엔 그 규칙을
안 옮겨서 DB 비밀번호가 든 `.env`가 업로드될 뻔했다. 빌드 로그의 "Detected .env
file, it is strongly recommended to use Vercel's env handling instead" 라는
문구를 보고서야 알아챘다 — 이 문구는 실은 "너 지금 .env를 커밋해서 올렸다"는
경고였다. 즉시 `.vercelignore`에 추가하고, 문제가 된 첫 배포는 삭제하고,
Supabase DB 비밀번호와 Kakao REST 키를 둘 다 재발급했다.

교훈: **ignore 파일을 새로 만들 때는 기존 것과 내용을 반드시 동기화한다.**
`.vercelignore`가 있으면 `.gitignore`는 (적어도 이번 케이스에서는) 무시되는
것으로 보였다.

### 대중교통 콜드스타트가 30~60초 걸렸다 — 원인은 DB 왕복

첫 배포에서 대중교통 등시선이 타임아웃 났다. 원인을 좁혀가는 과정:

1. Vercel Hobby 플랜은 Fluid Compute를 꺼두면 함수 실행시간이 **10초로 강제
   제한**된다. 코드에 넣은 `maxDuration = 30`은 이 설정이 켜져 있어야 적용된다.
   → 프로젝트 설정에서 Fluid Compute 켬
2. Function Region이 기본값(북미, iad1)이었다. DB(Supabase)는 서울인데 매
   요청마다 태평양을 왕복하고 있었다. → 서울(icn1)로 변경
3. 그래도 여전히 30~60초가 걸렸다. **진짜 원인은 minotor 그래프(16MB)를 매
   콜드스타트마다 DB(Postgres bytea)에서 새로 받아오는 구조 자체**였다 — 리전을
   맞춰도 16MB 바이너리를 매번 새로 받고 역직렬화하는 비용은 안 줄어든다.

이 그래프는 GTFS 원본을 새로 받을 때만 바뀌는 정적 데이터라는 걸 다시 떠올리고,
DB 저장을 버리고 **`src/data/transit-graph/`에 파일로 커밋해 배포 번들에
직접 포함**시키는 쪽으로 바꿨다. 네트워크 왕복 자체가 없어지니 콜드스타트가
2~4초로 줄었다(로컬 테스트 8초보다도 빠르다 — Vercel의 파일시스템 접근이
Postgres 왕복보다 훨씬 빠른 셈이다). `db/007_transit_graph.sql` 테이블은
DB에 남아있지만 이제 코드에서 안 쓴다.
