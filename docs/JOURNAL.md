## 2026-08-26 ~ 08-28 — 착수, 그리고 축 전환

### 시작점

*"자취방에서 가까운 근무지가 중요한 사람이 많은데 그걸 한눈에 보기가 힘들다"* 는 불편함에서 출발했다. 기존 채용 사이트는 `직무 → 공고 목록 → 주소 확인 → 지도 앱에 하나씩 찍기` 순서인데, 이걸 `내 위치 → 통근 30분 권역 → 그 안의 공고` 로 뒤집는 것이 아이디어였다.

### 첫 설계 판단

**비용 구조를 먼저 풀었다.** 순진하게 만들면 `사용자 N명 × 공고 M건` 만큼 길찾기 API 를 호출해야 한다. 공고 5만 건이면 사용자 한 명의 검색에 5만 콜이다.

해법은 방향을 뒤집는 것이었다. "각 공고까지 몇 분?" 이 아니라 **"내 위치에서 30분에 닿는 영역"을 폴리곤 하나로 계산**하고, 그 안의 대상을 PostGIS 공간 쿼리로 뽑는다. 5만 콜이 1콜이 된다. 여기에 출발지를 격자에 스냅해 `(격자, 모드, 분)` 키로 등시선을 영구 캐시하면, 같은 동네 두 번째 사용자부터는 라우팅 엔진을 아예 호출하지 않는다.

이 격자 스냅은 **개인정보 보호도 동시에 해결한다.** 사용자가 입력하는 출발지는 사실상 집 주소다. 격자로 스냅한 뒤에만 저장·캐시·로깅하면 캐시에서 개인의 집을 역추적할 수 없다.

**수집기를 지도보다 먼저 만들었다.** 공고는 마감되면 원본이 사라지고 소급 수집이 불가능하다. 지도는 나중에 다시 만들 수 있지만 놓친 시계열은 못 만든다.

### 스키마에서 중요했던 두 가지

**시계열을 구간으로 저장했다.** 일별 행으로 쌓으면 5만 공고 × 365일 = 1,800만 행이 되어 무료 티어를 넘긴다. `first_seen_on ~ last_seen_on` 구간으로 두고 일별 활성 수를 겹침 쿼리로 복원하면 무손실이면서 저장량이 두 자릿수 적다.

**수집 실패와 진짜 0을 구별했다.** 수집기가 조용히 실패한 날을 "대량 마감"으로 기록하면 시계열에 가짜 절벽이 생긴다. 이것이 이 프로젝트의 **유일한 회복 불가능한 손상**이라고 판단해, 소스를 끝까지 다 읽은 실행에서만 미관측 항목을 마감 처리하도록 했다.

### 실제로 잡힌 버그들

설계보다 이쪽이 더 값진 기록이다. 모두 **예외를 던지지 않고 조용히 데이터를 오염시키는** 유형이었다.

**① DB TLS 검증 우회** — 내가 처음 쓴 코드에 `rejectUnauthorized: false` 가 들어 있었다. 흔한 편법이지만 DB 연결이 중간자 공격에 노출된다. 제거하고 CA 인증서 검증을 필수화했다. 우회 플래그는 제공하지 않는다.

**② 날짜 시간대 왕복** — node-postgres 가 `date` 를 로컬 자정의 `Date` 로 파싱하고, 그것을 `toISOString()` 으로 문자열화하면 KST 에서 9시간이 빠져 **하루 전날**이 된다. 그 결과 **모든 공고에 매 실행마다 가짜 마감일 변경 이력이 쌓이는** 상태였다. 스모크 테스트가 잡았고, 타입 검사로는 절대 잡히지 않는다. `DATE` 를 문자열로 받도록 근본 차단했다.

**③ 적재 성능** — 건당 쿼리 4번 구조였다. 전국 10만 건이면 왕복 40만 번이고 왕복 30ms 만 잡아도 3시간이 넘는다. 수집이 늦어지면 시계열에 결측이 생기므로 이건 성능이 아니라 기능 문제였다. `jsonb_to_recordset` 으로 JSON 을 파라미터 하나로 넘겨 청크당 쿼리 1~2개로 바꿨다. Postgres 의 65,535개 파라미터 제한도 함께 피한다.

**④ 인라인 주석이 값에 섞임** — `.env` 에 `COLLECT_MAX_PAGES=0  # 0 = 무제한` 처럼 쓰면 dotenv 버전에 따라 주석이 값에 들어와 `Number()` 가 `NaN` 이 된다. 수집 페이지 상한이 조용히 깨지는 경로였다.

**⑤ 법정동코드 페이징 누락** — 행정표준코드 API 는 리·동까지 전부 반환하고 시군구 행이 그 안에 흩어져 있다. 첫 페이지(1,000행)만 읽으면 리가 많은 도의 뒤쪽 시군구가 통째로 빠진다. 경상북도 7건 → 24건, 전국 169건 → **269건**. 이대로 뒀다면 경북·충남 매물이 지도에서 사라지는데, *데이터가 있는데 없는 것처럼 보이는* 종류라 발견이 아주 늦었을 것이다.

### 채용 데이터가 막힌 과정

여기서 프로젝트가 흔들렸다. 접근 경로를 하나씩 실측했다.

| 소스 | 결과 |
|---|---|
| 고용24 채용정보 API | **개인회원 런타임 차단.** 활용신청은 자동승인 되었는데 호출 시점에 기관구분 `개인` 을 거부한다. 문서에 이 제한이 없어 호출해봐야 드러난다. 호스트 2종 × 파라미터 2종 × XML/JSON 5가지 변형 모두 동일 |
| 공공데이터포털 워크넷 | 자동승인이지만 **KOGL 제4유형 = 비상업적 이용만** |
| 사람인 오픈API | 심사. 근무지 해상도가 **시군구까지**(`서울 > 관악구`), 일 500회 |
| 잡코리아 API | **공공기관·학교 우선 제공.** 기업·개인은 내부 검토 |

중간에 "그럼 사람인을 크롤링하자" 는 방향이 나왔지만 접었다. **잡코리아가 사람인을 상대로 낸 소송에서 법원이 채용공고 크롤링을 저작권법상 데이터베이스제작자 권리 침해로 인정했다.** 하려던 것과 거의 동일한 행위이고, 그 사건의 피고가 사람인이었다. 무엇보다 사람인은 공식 API 를 제공하므로 크롤링할 이유가 없다.

결론: **승인에 의존하는 어떤 경로도 수익화를 지탱하지 못한다.** 채용 공고 데이터는 잡보드의 사업 그 자체여서 개방할 인센티브가 없다.

### 축 전환 — 통근 기반 거주지 지도

원래 구상의 **거울상**으로 옮겼다. "자취방에서 가까운 근무지" 대신 **"직장에서 가까운 거주지"**. 통근 엔진은 그대로다.

전환 근거는 데이터 구조의 차이였다.

| | 채용 데이터 | 국토부 전월세 실거래가 |
|---|---|---|
| 개인 접근 | 런타임 차단 | 자동승인 |
| 상업적 이용 | KOGL 제4유형 | **이용허락범위 제한 없음** |
| 트래픽 | 500회/일 | 10,000회/일 |
| 주소 해상도 | 시군구 | 건물 단위 |

정부가 개방 의무를 지는 데이터라 구조가 다르다. 그리고 수익 모델은 오히려 개선된다 — 사용자가 통근권과 예산을 확정한 **직후의** 트래픽이 부동산 업계에서 가장 값이 높고, 우리는 매물을 갖지 않고도 그 트래픽을 만든다. 실제 매물은 네이버부동산·직방 검색 딥링크로 넘긴다. 크롤링이 0이다.

**만든 것은 거의 버리지 않았다.** 핵심 자산은 좌표 해결 엔진이고 그건 도메인 중립이다. 채용 스키마와 수집기도 테스트 통과 상태로 남겨뒀다. JSON-LD 수집기가 준비되면 레이어로 얹어 `출근지 ↔ 거주지` 양방향을 완성한다.

### 핵심 자산 — 좌표 해결 엔진

공개 데이터는 좌표를 주지 않고 주소 해상도가 시군구~법정동 수준이다. 관악구 중심점으로 통근시간을 계산하면 구 하나가 동서 5km 이므로 "도보 30분 이내" 필터가 의미를 잃는다.

착안점은 **`고유명 + 지역` 키워드 검색**이었다. 실측:

```
상세주소 "성남시 분당구 판교역로 166" → (127.11045, 37.39530)
이름+지역 "카카오 경기 성남시 분당구"  → (127.11046, 37.39545)   약 1m 차이
"래미안대치팰리스 서울 강남구"        → 서울 강남구 삼성로51길 37
"헬리오시티 서울 송파구"              → 서울 송파구 송파대로 345
```

**정확도 낮은 좌표를 격리하는 것이 이 엔진의 절반이다.** 해결 실패나 중심점 폴백은 `commute_usable=false` 로 표시해 통근시간을 표시하지 않는다. 정확도 낮은 좌표로 통근시간을 계산해 보여주면 지도가 조용히 거짓말을 하게 되고, 그것이 이 제품에서 가장 나쁜 실패다.

### 문서를 믿지 않고 실측한 것들

**엔드포인트와 필드명은 문서가 틀렸다.** 실거래가 API 문서에는 필드명이 한국어(`보증금액`, `월세금액`)로 적혀 있지만 실제 응답은 영문 camelCase(`deposit`, `monthlyRent`)다. 문서를 믿고 매핑했다면 전 필드가 `null` 로 적재되면서도 예외는 나지 않는, 가장 찾기 어려운 형태로 깨졌을 것이다.

그래서 **탐색기 스크립트**를 먼저 만드는 방식으로 굳혔다. 후보 엔드포인트를 순회해 동작하는 것을 찾고 **실제 응답 필드와 값을 덤프**한다. 이 방식으로 워크넷·실거래가·법정동코드 세 API 를 모두 확정했다.

값 덤프로 잡은 가장 중요한 것은 **금액 단위**다. `deposit="70,000"` 은 7억원이다 — 만원 단위 + 쉼표 포함 문자열. 틀려도 예외가 나지 않고 시세만 1만배 어긋난다. 단위 테스트로 고정했다.

**행정구역이 바뀌어 있었다.** 광주광역시와 전라남도가 `전남광주통합특별시` 로 통합되어, 구 명칭으로 조회하면 데이터가 없다고 응답한다. 이것이 좌표 해결기에도 파급됐다 — 법정동코드는 통합 명칭을 쓰는데 지오코딩 결과 표기가 다르면 지역 검증이 둘을 다르다고 판정해 **광주·전남 전체가 통근 계산에서 빠진다.** 시도명 별칭 그룹으로 묶고 회귀 테스트를 추가했다.

### 첫 실측 결과 (강남구 2026-08, API 4회)

```
거래 1,343건 / 건물 564건
아파트     보증금 3.00억 / 월세 155만   79.8㎡
오피스텔   보증금 2,000만 / 월세  85만   24.7㎡
연립다세대  보증금 5,000만 / 월세  68만   30.0㎡
단독다가구  보증금 1,000만 / 월세  70만   33.0㎡
```

시세가 현실적이므로 금액 단위가 맞다는 것이 확인된다.

좌표 확정 결과:

```
아파트 215/215, 오피스텔 66/66, 연립다세대 271/271 → 전부 건물 정밀도
단독다가구 0/12 → 법정동 중심점
건물 기준 97.9% / 거래 기준 83.7%
```

**거래 기준 83.7% 가 정직한 숫자다.** 단독/다가구는 건물 1개가 수십 건의 거래를 대표하므로 건물 기준 비율은 품질을 과대평가한다. 남은 16%는 정부가 개인정보 보호로 지번을 제공하지 않는 구조적 한계다.

**판정: 제품이 성립한다.** 아파트·오피스텔·원룸(연립다세대)은 건물 단위 통근 계산이 100% 가능하다.

### 이 프로젝트에서 굳어진 원칙

1. **문서를 믿지 말고 실측한다.** 탐색기 스크립트를 먼저 만든다
2. **조용한 실패를 만들지 않는다.** 실패와 "진짜 0"을 데이터에서 구별한다
3. **정확도를 데이터에 명시한다.** 못 믿을 값은 격리하고, 격리했다는 사실을 표시한다
4. **원본을 보존한다.** 매핑이 틀려도 무손실 재처리가 가능하도록 `raw` 를 남긴다
5. **외부 데이터를 쓰기 전에 라이선스와 개인 접근 가능성을 확인한다.** 이걸 놓쳐서 축을 한 번 바꿨다

## 2026-08-29 — 전국 수집, 그리고 4개 도가 통째로 저품질이던 버그

### 전국 데이터 수집

최근 3개월 × 269개 시군구 × 주택 4종 = 3,228슬롯.

```
API 호출 3,264회 (예산 9,000)
거래 396,262건 / 건물 73,062곳 / 시군구 256개
0건 슬롯 583  실패 슬롯 0  적재 실패 0
```

일 10,000회 한도의 33%만 썼다. 슬롯당 1회를 거의 넘지 않았는데, 시군구 1개월 거래가 대부분 1,000건(페이지 크기) 이하라 페이징이 필요 없었기 때문이다.

0건 슬롯 583개는 실패가 아니라 **실제로 거래가 없는 조합**이다(지방 소도시의 오피스텔 등). 이 둘을 구별해 기록한 설계가 여기서 값을 했다. 구별하지 않았다면 "시세 없는 지역"으로 오염됐을 것이다.

### 실행 전에 잡은 버그: 일시적 실패의 영구 캐시

7만 건 지오코딩을 시작하기 직전에 발견했다. `kakaoFetch` 가 HTTP 오류·재시도 소진에도 `null` 을 돌려줘서, 호출부가 "주소 없음" 과 구별할 수 없었다. 그 결과가 `geocode_cache` 에 miss 로 저장되고, 재실행하면 캐시가 먼저 걸려 되살릴 수 없다.

**중간에 쿼터가 끊기면 남은 수만 건이 전부 영구 실패로 굳는 구조였다.** `GeocodeUnavailableError` 를 도입해 '일시적 불가' 와 '주소 없음' 을 분리하고, 배치는 이 예외를 받으면 남은 건물을 건드리지 않고 중단하도록 했다.

함께 병렬화했다. 순차로는 건당 왕복 200ms 로 4시간이 넘는다. 워커 6개 + 250건 배치 쓰기로 **초당 70건**이 되어 20분 안에 끝났다.

### 그리고 실제로 잡힌 버그: 도 이름 축약형

지오코딩 후 통근 계산 가능 비율이 거래 기준 68.3% 였다. 단독/다가구(구조적 한계)를 빼고도 **아파트 3,796곳이 시군구 중심점으로 떨어져** 있었다. 도로명주소가 100% 있는데도.

시도별 분포가 원인을 가리켰다.

```
경상남도 1,777   경기도    10
충청남도 1,407   인천광역시  6
경상북도 1,112
충청북도   872
```

실패의 **99.6%가 딱 4개 도**. 지방 주소가 어려운 문제가 아니었다.

라이브로 다시 물어보니 모든 질의가 building 정밀도로 성공했다. 즉 **질의는 성공했는데 결과를 우리가 거부**하고 있었다.

```
법정동코드: "충청남도"  → 접미사 '도' 제거 → "충청남"
Kakao 반환: "충남"                        → "충남"
            "충청남" ≠ "충남"  →  거부  →  중심점 폴백
```

`shortSido()` 가 접미사만 떼고 축약형을 몰랐다. 서울·경기·인천은 축약형이 정식명과 같아서 멀쩡했고, **충청남/충청북/경상남/경상북 네 도만** 걸렸다. 전라남·전라북은 통합 별칭 그룹에 이미 들어 있어 우연히 피해 갔다.

축약형 매핑을 추가하고 4개 도 회귀 테스트를 넣었다. `--improve` 재실행 결과:

```
아파트     3,797/3,803 (99.8%)
연립다세대    916/  919 (99.7%)
오피스텔      466/  478 (97.5%)
```

전체 통근 계산 가능 비율이 **거래 기준 68.3% → 75.5%** 로 올라갔다.

### 이 버그가 남긴 교훈

예외가 나지 않았다. 로그도 깨끗했다. 4개 도의 아파트가 조용히 3km 오차 중심점에 찍혀 있었을 뿐이다. **강남구만 검증했을 때는 100% 였다** — 서울은 축약형이 같으니까.

수도권 표본만으로 검증하면 지방에서만 나는 버그를 못 잡는다. 그리고 이걸 발견한 것은 테스트가 아니라 **"왜 이 숫자가 이렇지" 를 파고든 것**이었다. `stats:rent` 가 전략별·유형별 분포를 출력하지 않았다면 68.3% 를 그냥 받아들였을 것이다.

관측 지표를 만들어 두는 것이 테스트만큼 중요하다.

### 현재 상태

```
건물 73,062 (좌표 100%)   거래 396,262   시군구 256/269
통근 계산 가능: 건물 94.6% / 거래 75.5%
남은 24.5%는 전부 단독·다가구 (정부가 지번을 공개하지 않는 구조적 한계)
```

## 남은 한계 (정직하게)

- 실거래가는 **과거 거래**이지 현재 매물이 아니다. "지금 계약 가능한 방"은 제공하지 않는다
- 실거래 레코드에 고유 ID 가 없고 동/호 정보도 없어, 모든 조건이 같은 두 계약은 **원리적으로 구별 불가**다. 재수집 중복을 막기 위해 동일 거래로 취급하며 실측에서 1.5%가 합쳐졌다. 시세 중앙값에는 영향이 거의 없다
- 단독/다가구(거래 기준 16%)는 건물 단위 좌표를 얻을 수 없다
- 라우팅 엔진은 이 프로젝트에서 유일하게 무료 티어에 들어가지 않는다
